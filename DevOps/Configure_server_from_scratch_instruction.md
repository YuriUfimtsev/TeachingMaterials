# Инструкция по настройке сервера для развертывания на нём веб-сервиса 
#### Вдохновлено опытом с HwProj

В документе рассмотрены необходимые шаги для настройки сервера: установка и конфигурация ОС, организация удаленного доступа, подготовка окружения для развертывания веб-сервиса. Используются nginx+certbot, ufw, docker и другие утилиты UNIX.

## Установка ОС. Ubuntu 24.04 Server
Предварительно подготовив загрузочную флешку с дистрибутивом, вставляем её в usb-порт серверного ПК. Перезагружаем систему с попаданием в UEFI/BIOS: выбираем загрузку с USB-носителя. На ubuntu перезагрузиться и попасть в UEFI/BIOS можно так: `sudo systemctl reboot --firmware-setup`.

Также если были на ubuntu, можно сначала настроить порядок загрузки и просто перезагрузиться.
```sh
sudo efibootmgr
# меняем порядок через efibootmgr —bootorder xxxx,yyyy,... -v
sudo reboot
```

Устанавливаем систему.
1. **Try or install Ubuntu Server**
2. **English**
3. **English (US)** (конфигурация клавиатуры)
4. Выбираем стандартный тип установки: **Ubuntu Server**
5. Сетевой интерфейс должен сам подтянуться (например, **enp1s0**)
6. Пропускаем настройку **Proxy configuration**
7. Ждем, пока mirror address пройдёт проверку (**This mirror location passed tests**)
8. Настраиваем разметку диска. Убираем галочку с LVM: обычно этот менеджер томов избыточен. Оставляем выбранным только опцию **Use an entire disk**
9. Проверяем **Storage configuration**. Например, в **FILE SYSTEM SUMMARY** видим две точки монтирования: **/** и **/boot/efi** 
10. Придумываем имя текущего пользователя и пароль. Также вводим **Servers name**: позже имя хоста можно будет поменять через команду **hostname**
11. Пропускаем предложение обновиться до платной Ubuntu Pro
12. Ставим галочку на **Install OpenSSH Server**
13. Никакие snap-пакеты не устанавливаем (хотя, дело вкуса. Если решили управлять пакетами через snap, а не apt-менеджер, то можно и на этом шаге начать)
14. Дожидаемся окончания настройки системы и надписи **Installation complete!**
15. Перезагружаемся через **Reboot Now**. Может появиться сообщение, что система выполнила размонтирование загрузочной флешки. Всё ок: нужно просто её достать из usb-порта. 


Готово. Теперь Вы подключены к системе от лица пользователя, введенного ранее.

## Первые шаги после установки ОС: обновление пакетов и настройка удаленного доступа
Первым делом важно обновить существующие пакеты.
```sh
sudo apt update
sudo apt upgrade -y
```

Дальше для удобства настройки ОС организуем себе удаленный доступ.
Предварительно на ПК, с которого планируем удаленно подключаться, сгенерируем ssh-ключи (например, через **ssh-keygen**). Вынесем публичный ключ на флешку, эту флешку вставляем в usb-порт серверной машины.

Монтируем флешку.
```sh
# Смотрим название этого внешнего диска в списке. Например, им может быть sdb1
sudo fdisk -l

# Создаем произвольную папку и монтируем в неё данные флешки
sudo mkdir /mnt/usb
sudo mount /dev/sdb1 /mnt/usb
```

Теперь копируем ключ в **authorized_keys** своего пользователя и суперпользователя (**root**). Также настраиваем права: этот шаг очень важен. В будущем не меняйте права к файлу **authorized_keys** и папке **.ssh** в целом: так легко можно лишиться удаленного доступа к серверу.
```sh
# В папке своего пользователя (/home/username/ <=> ~) создаем .ssh директорию
cd ~
mkdir .ssh

# Устанавливаем именно такие права доступа
sudo chmod 700 .ssh

# в файл .ssh/authorized_keys копируем ssh-ключ пользователя и настраиваем права 
cp /mnt/usb/...(путь к файлу с публичный ключем) /home/(имя_пользователя)/.ssh/authorized_keys
chmod 600 .ssh/authorized_keys

# Аналогично для суперпользователя. Может потребоваться перейти в режим root через команду sudo su
cd /root/
... (повторяем команды выше)
```

Теперь размонтируем флешку и достанем её.
```sh
sudo umount /mnt/usb

# Можно посмотреть список устройств и убедиться, что успешно размонтировали флешку
lsblk 
```

Напоследок убедимся, что SSH-демон установлен, и запустим его.
```sh
sudo apt update

# Если не установлен, выполним `sudo apt install openssh-server`
sudo systemctl status ssh

sudo systemctl enable ssh
sudo systemctl start ssh
```

Теперь со своего ПК, содержащего непубличный ssh-ключ, проверим подключение: `ssh (имя пользователя)@(ip-сервера)`. Если всё правильно настроено, должны успешно подключиться к серверу.

## Работа с пользователями: создание профилей и настройка удаленного доступа
Чтобы обеспечить удаленный доступ к системе для других пользователей будем работать с утилитой **adduser**. Для каждого нового пользователя выполняем следующий "скрипт".
```sh
# Можем пропустить все шаги, кроме создания пароля. Пароль запоминаем!
sudo adduser имя_пользователя

# Добавляем пользователя в группу с правами sudo
sudo usermod -aG sudo имя_пользователя

# Можем проверить группы пользователя
groups username

# Дальше устанавливаем требование смены пароля при первом подключении пользователя
sudo passwd --expire имя_пользователя

# Убедимся, что пароль потребуют поменять. В первых трех строчках вывода команды должно быть "password must be changed"
sudo chage -l имя_пользователя
```
Теперь сообщаем пользователю временный пароль и берем его публичный ssh-ключ. Кладем ssh-ключ в папку пользователя: **/home/имя_пользователя/**. Пример того, как это можно сделать, описан выше в главе **Первые шаги после установки ОС**. 

Важно отметить, что теперь можем передавать файлы на сервер удаленно с помощью **scp**. Например, `scp C:/../.. root@(ip_сервера):/home/имя_нового пользователя/.ssh/authorized_keys`.

Важно настроить права на "владение" папкой .ssh для пользователя через `chown`.
```sh
sudo chown -R имя_пользователя:имя_пользователя /home/имя_пользователя/.ssh/
```

Готово. Пользователю осталось попробовать удаленно подключится к серверу: `ssh (имя_пользователя)@(ip-сервера)`.

## Настраиваем окружение для веб-сервиса
**Установим докер**: смотрите команды на https://docs.docker.com/engine/install/ubuntu/#install-using-the-repository.

Настроим nginx+certbot для развертывания по ssh. Перед этим необходимо получить у провайдера внешний ip-адрес (например, сообщив mac-адрес серверного ПК) и настроить А-записи в регистраторе домена.
```
A @ -> ip_адрес_сервера
A www -> ip_адрес_сервера
```

###  Настраиваем nginx
```sh
sudo apt update
sudo apt install nginx # Если вдруг не установлен
```

Конфигурировать nginx будем через файл `/etc/nginx/sites-available/default`. При любом изменении будем выполнять `sudo nginx -t` для проверки сиснтаксической корректности конфигурации, `sudo systemctl restart nginx` для применения изменений.

Nginx должен будет создать default файл по умолчанию.
Однако ниже привожу пример базовой http-конфигурации.
```nginx
server {
    listen 80;
    server_name example.com www.example.com;
    root /var/www/example.com/html;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
```
Ниже пример базовой https-конфигурации (основан на конфигурации hwproj.ru).

```nginx
server {
    server_name hwproj.ru;

    # Корневая директория файлов фронтенда
    root /home/hwproj_user/docker/HwProj-2.0.1/hwproj.front/static_dist;

    location / {
        try_files $uri $uri/ /index.html;
        error_page 502 504 @handle_unavailable;
    }

    # Реверс-прокси для бэкенда
    location /api {
        proxy_pass	http://localhost:5000/api;
    }

    # Обработка ошибок
    location @handle_unavailable {
        root /var/www/html/errors;
        try_files /while_restart.html = $status;
    }

    # Для доступа к кастомной странице, отображающейся при ошибках
    location /errors_static/ {
        internal;
        root /var/www/html/errors;
    }

    listen 443 ssl; # managed by Certbot
    ssl_certificate /etc/letsencrypt/live/hwproj.ru/fullchain.pem; # managed by Certbot
    ssl_certificate_key /etc/letsencrypt/live/hwproj.ru/privkey.pem; # managed by Certbot
    include /etc/letsencrypt/options-ssl-nginx.conf; # managed by Certbot
    ssl_dhparam /etc/letsencrypt/ssl-dhparams.pem; # managed by Certbot
}

# Редирект с HTTP на HTTPS
server {
    if ($host = hwproj.ru) {
        return 301 https://$host$request_uri;
    } # managed by Certbot

	server_name hwproj.ru;
    listen 80;
    return 404; # managed by Certbot
}
```

### Настраиваем работу с сертификатами через certbot (для доступа по https)
```sh
# Устанавливаем certbot
sudo apt install certbot python3-certbot-nginx

# Конфигурируем. Вместо example.com свой домен. Например, hwproj.ru
sudo certbot --nginx -d example.com -d www.example.com
```
Дальше certbot сам обновит конфиг Nginx для работы с https. Перезапускаем nginx.
```sh
sudo nginx -t
sudo systemctl reload nginx
```

## Настройка фаервола
Для работы с файрволом будем использовать утилиту **ufw**. Изначально демон не запущен.
Разрешаем доступ к портам 80 и 443 для подключений по http и https. Также перед запуском ufw важно разрешить подключение к 22 порту, иначе ssh-подключение отвалится.

```sh
sudo ufw allow ssh # Или allow 22
sudo ufw allow 'Nginx Full' # Или allow 443; allow 80

# Для того, чтобы запретить соединения по определенному порту, используйте
# sudo ufw deny

# Проверим, что порт ssh (22) открыт. До запуска ufw!
sudo ufw status verbose

sudo ufw enable
sudo ufw status
```
Также для обеспечения безопасности закрывайте порты, специфичные для веб-сервиса. Например, для HwProj это бэкенд на 3000 и фронтенд на 5000.

## Дополнительная конфигурация
Чтобы отключить возможность подключаться к серверу без ssh-ключа по паролю изменим конфиг ssh-демона.

```sh
sudo vim /etc/ssh/sshd_config

# Проверяем/изменяем следующие строки
PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys
PasswordAuthentication no

# Сохраняем файл и применяем изменения
sudo systemctl restart ssh
```

Чтобы ssh-соединение постоянно не обрывалось после n секунд бездействия, на своем ПК в .ssh/config рекомендуется добавить следующию строку.
```
Host *
    ServerAliveInterval 30
```

### Настройка **rclone** и **cron**
Если потребовалось организовать выгрузку по времени (например, для работы с бэкапами), важно сконфигурировать **rclone** для доступа к удаленным хранилищам и **cron** для исполнения sh-скриптов по времени.

#### Настройка **rclone**.
```sh
# Устанавливаем rclone
sudo apt install rclone
```
Дальше про настройку доступа к Яндекс.Диску смотреть [здесь](https://www.dmosk.ru/miniinstruktions.php?mini=rclone-example#yandex).

Вкратце: самый простой вариант пройти аутентификацию через редирект и подтверждение разрешений в браузере. Однако у сервера браузера нет, поэтому проходим проверки через rclone на любом другом ПК, получаем токен и кладем его на сервер: /root/.config/rclone/rclone.conf

#### Настройка **cron**
Довольно просто: через `sudo crontab -e` задаем в файле правила исполнения скриптов.
```
40 4,20 * * * sudo /home/hwproj_user/docker/HwProj-2.0.1/backups_builder.sh >> /var/log/cron/backups_builder.log 2>&1
```
Например, правило выше говорит: "в 4:40 и 20:40 по UTC запускай команду исполнения скрипта `sudo /home/hwproj_user/docker/HwProj-2.0.1/backups_builder.sh` и вывод вместе с ошибками направляй в `/var/log/cron/backups_builder.log`".

Посмотреть добавленные правила можно через `sudo crontab -l`.


## Полезные команды для работы с сервером
Команды, умение работать с которыми существенно ускорит процесс настройки сервера.

```sh
# Работа с архивами
# Создать архив папки
tar -czvf archive_name.tar.gz /path/to/folder
# Извлечь данные из архива
tar -xzvf archive_name.tar.gz -C /path/to/extract

# Выдача прав. Например, a+x: для всех пользователей разрешить исполнение этого файла. Выданные права можно смотреть через `ls -ahl`
sudo chmod a+x / u-r / ...

# Посмотреть свой внешний (публичный) ip
curl ifconfig.me

# Для редактирования файлов удобно использовать vim
sudo vim # для возможности редактирования любых файлов
esc # для смены режима работы с vim
:q # выйти из vim
:wq # выйти из vim, сохранив изменения
:q! # выйти из vim, сбросив изменения
i # переход в режим редактирования
yy # скопировать текущую строку
p # вставить скопированную строку
dd # удалить текущую строку
```
